4) LAS COMPROBACIONES DE INTEGRIDAD NO SON VACIAS

   a) La invariante se ejecuta sobre datos reales en la base viva:

$ docker compose exec -T db psql -U openlibrary -X -d openlibrary \
    -c "select status, count(*) from copies group by status order by status;" \
    -c "select returned_at is null as abierto, count(*) from loans group by 1;"
  status   | count
------------+-------
 DISPONIBLE |    92
 PRESTADO   |     1
(2 rows)

 abierto | count
--------+-------
 f      |     1
 t      |     1
(2 rows)

   Hay 1 copia PRESTADO y exactamente 1 prestamo abierto: el chequeo tiene algo que
   comprobar, no esta siempre a cero por casualidad.

   b) Control negativo: meto una violacion a proposito y el chequeo la detecta.
      Restauro el dump en una base sonda, marco una copia DISPONIBLE como PRESTADO
      sin prestarlo, y lanzo la misma consulta que usa el script:

$ ... pg_restore -h db -U openlibrary --no-owner --no-privileges -d probe_t2 /backups/manual-check.dump
$ ... psql -d probe_t2 -c "update copies set status='PRESTADO' where id = (select min(id) from copies where status='DISPONIBLE');"
 prestadas_sin_prestamo
------------------------
                      1
(1 row)

   Detecta la violacion: devuelve 1, no 0. Ese 1 es justo lo que hace el script en
   su linea 143-149 (si n != "0" -> rc=1), o sea que la corrida habria terminado
   con "VEREDICTO: FALLO" y exit 1. Aqui no se ejecuto el script entero sino la
   consulta aislada sobre la base sonda, para poder meter la violacion a proposito.

   c) El segundo chequeo, `copies.location_id huerfano`, solo puede dar != 0 si la
      restauracion NO trajo las constraints, porque la FK lo impide. Comprobado:

$ ... psql -d probe_t3 -c "select count(*) ... not exists (select 1 from locations ...);"
0                                        <- FK restaurada
$ ... psql -d probe_t3 -c "ALTER TABLE copies DROP CONSTRAINT copies_location_id_fkey;" \
                 -c "update copies set location_id=999999 where id=(select min(id) from copies);"
$ ... psql -d probe_t3 -c "select count(*) ... not exists (select 1 from locations ...);"
1                                        <- restore sin constraints
DROP DATABASE

   Sin la FK, Postgres rechaza el huerfano:

ERROR:  insert or update on table "copies" violates foreign key constraint "copies_location_id_fkey"
DETAIL:  Key (location_id)=(999999) is not present in table "locations".

   O sea: el chequeo es tautologico con el esquema completo, y su unico valor real
   es confirmar que pg_restore trajo las claves foraneas. Se mantiene porque es
   gratis y detecta exactamente ese fallo, pero no esperes que encuentre un bug de
   datos que la base viva ya prohibe.

5) COMPATIBILIDAD

   - POSIX sh + `set -eu`. Sin `local`, sin `[[ ]]`, sin arrays, sin `function`.
     Sin shellcheck instalado en esta maquina, revisado a mano.
   - En Git Bash hay que exportar MSYS_NO_PATHCONV=1 (lo hace el propio script):
     si no, MSYS convierte "/backups" en "C:/Program Files/Git/backups" antes de
     llamar a docker.exe y el script no encuentra ningun dump.
   - Tambien funciona desde un subdirectorio: docker compose sube hasta el compose
     file. Verificado ejecutandolo desde scripts/.
   - Todo lo que el script IMPRIME es ASCII a proposito. La salida con acentos
     capturada desde Git Bash sale como mojibake (ver docs/evidence/round-0/
     verify-restore.txt) y un log ilegible no es evidencia.
